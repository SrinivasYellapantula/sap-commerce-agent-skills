## .19 cache-provider implementation decisions

- SAP documents `CXEC-68918` for reduced Caffeine cache effectiveness during concurrent bulk processing, with SAP Note `3809931` as access-qualified follow-up evidence. Do not claim the note was fully reviewed without authorized content.
- Default decision: keep Caffeine active. The `.19` target says no changed behavior or additional action is required unless the application is affected. A version-pin update and cache regression tests are straightforward; enabling or activating Ehcache 2 is conditional.
- Before any fallback patch, identify custom cache-region beans/subclasses and all affected batch, cronjob, integration, import, indexing, or business flows. Capture current `.17` hit rates, database query volume, throughput, latency, data volume, cache sizes, and concurrency. When available, retain the pre-JDK21/JDK17 benchmark because SAP's validation guidance compares against that behavior.
- Run an approved production-like test at or above peak concurrency. A low-concurrency developer run is not acceptance evidence. If results regress, prepare three separately reviewable approaches: improve data-processing queries/aggregation; tune sizes or isolate entity types; enable targeted Ehcache 2 regions. A global switch is an emergency or evidence-backed fallback, not the first patch.
- Packaging fallback capability requires adding SAP's optional `legacyehcache2cacheprovider` extension to the verified extension list and rebuilding/deploying `2211-jdk21.19`. The target supplies Ehcache `2.10.9.2`; do not add a project-managed JAR. Merely setting the provider property without the extension is not a complete plan.
- Provider activation is a distinct environment/config change followed by pod restart: `regioncache.<lower-case-region-name>.cacheprovider=ehcache2` for targeted rollback, or `regioncache.cacheprovider=ehcache2` globally. Reverting the property to `caffeine` and restarting is the configuration rollback. Adding or removing the extension remains a build/deployment change.
- For Ehcache 2 regions, use `regioncache.cacheprovider.ehcache2.evictionpolicy` or `regioncache.<region>.cacheprovider.ehcache2.evictionpolicy`, with `FIFO`, `LRU`, or `LFU`. Do not resurrect removed `regioncache.<region>.evictionpolicy` properties. Confirm exact lower-case region keys from the `DefaultCacheRegion` constructor name.
- Scan `DefaultCacheRegion`, `EhCacheRegion`, constructor wiring, `init()`, `createCacheStatistics`, `createCacheConfiguration`, `createCacheEventListener`, `compareAndSetMaxReachedSize`, `getCacheMap`, and `setCacheMap`. Classify any missed JDK21 cache API migration as a pre-existing blocker uncovered by the `.19` readiness scan.
- Acceptance requires the same workload before and after each change, cache hit-rate and database-query comparison, application and database saturation checks, restart verification, and a rollback drill. Record per-region versus global choice, property source/precedence, aspect/persona scope, and observability owner in the decision pack.

## Data Hub: .17 and .18

Inventory Data Hub Adapter clients, authorities, grants, import destinations and deployment scripts. Before deploying the patched adapter, add `ROLE_DATAHUBADMINGROUP` while preserving every existing required authority. Never replace the existing set with a copied two-role example. Data Hub is a confidential service client, not a browser PKCE client. Password grant is unsupported; re-read the tutorial including its now-required step 12 to determine the complete current configuration rather than guessing from the step number.

Plan authority update -> obtain a fresh token -> deploy patched adapter -> publication/import smoke test. If imports already return HTTP 403, correct the authority and obtain a new token; tokens issued before the change do not gain the role retroactively. Do not log token values or remove security checks to restore imports. Track SAP Note 3771065 as an access-qualified security source, not proof that its complete remediation was read.

For .17, scan essential-data copies of `essentialdata_2_b2bcommerce.impex` and `B2BCustomerEmailConstraint` annotation imports for `forceWrite`. Compare the target SAP file and prepare the documented corrected import; do not strip `forceWrite` from unrelated data. Verify repeat imports and constraint behavior in an approved dev environment.

Also test custom order-management strategy aliases and OCC `common-web-spring.xml` overrides: .17 fixes can make previously bypassed customization effective. SAP Note 3785483 is a follow-up source when applicable.

## .18 backend behavior, type system and operations

- Scan `defaultCommerceWebServicesCartService`, `defaultCartValidationStrategy`, and `cartValidationStrategy`. The target now respects the alias. Normally this is verification-only: test custom validation and OCC cart flows before proposing any code patch.
- Inspect `CouponService`, custom `CommerceCartCalculationStrategy` and calculation hooks. `couponservices.recalculate.with.cartcalculationstrategy` defaults to true; test coupon apply/release, quote discounts and transaction behavior. A false compatibility setting is an explicit temporary decision with regression evidence and a follow-up, not the default migration.
- For the documented promotion-evaluation NPE involving interacting product-discount rules and nested `and`/`exists` with `CartRAO(entries contains ...)`, inspect generated rules and SAP Note 3795772 if accessible. Verify the target default `drools.rulenetworkevaluator.breakOnDuplicateTuple=false`; test the affected rules and loop/completion behavior. Do not toggle globally for unrelated promotion errors.
- For distributed `SolrIndexerJob` with a read-only replica, test full indexing across all stages. Search custom processors and `SolrIndexerDistributedProcess.sessionUseReadOnlyDataSource`; the target fix addresses missing-process failures. Record a regression test rather than inventing a mandatory custom property patch.
- Inspect `UserTokenRevocationInterceptor` constructor calls and XML arguments. The one-argument `OAuth2RevocationTokenService` constructor is deprecated; target replacement takes `TokenService, ConfigurationService`. Verify the signature and wiring in target source/API evidence and test revocation. Do not call the old constructor removed without evidence.
- Read both sides of the Spring changes report for custom configuration-service, REST credential-provider, Integration API, indexing, digital-payment, coupon, warehousing and CPQ/CPS bean overrides. Names in a clipped PDF column are scan candidates, not replacement instructions.
- Reconcile type changes for fiscal-ID fields/rules, `SAPBDCPayloadMedia.forDeletion`, and wishlist product fields with custom impex, serializers, cleanup jobs and system-update plans. New types alone do not justify invented data migrations.
- For external-product wishlists, inspect `Wishlist2Entry.productCode`, optional `product`, `BaseStore.wishlistProductCodeFormatPattern` and `wishlistProductExistenceCheckSkipped`. If the feature is chosen, test missing product models, format validation, populators and OCC responses. Do not enable it for every store.
- Inventory references to SAP-shipped `.jks` files and keystore type settings. The PKCS12 notice concerns a future bundled-file transition; custom JKS remains supported by Java. Verify target-distribution files before changing paths, formats or secrets.
- Recheck Solr validity at deployment time: the PDF listed 9.10 and a 9.8 validity end of 2026-08-31 while still describing 9.8 as the manifest default. An implicit/default version is not proof of support. Validate explicit Solr version, target configset and indexing plan; never infer a Solr Lucene setting from Data Hub's separate Lucene libraries.

Retain the earlier detailed retry/OAuth/proxy/SSL/reactive-contract matrix.
